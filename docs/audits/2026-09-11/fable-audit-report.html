Fork audit: two weeks of commits

38 merges onto main between 3 and 11 September, reviewed for accidental regressions and for changes that fight the way you actually use this app.

Reviewed at 523b4be4. Test suite green: 36 suites, 205 tests. Scoped typecheck passes. Nothing in this report has been changed; it is all observation.

The short version. The CSV revert was not a one-off. The same instinct that added a 10 MB file cap and a 50,000 row cap to a local CSV importer also added a 31 day cap to the trip distance chart, a 31 day ceiling on the Voi availability API, and a rule that throws away an entire ten minute Voi snapshot if one vehicle record is malformed. I found four of these, plus one genuine wiring bug that can hang the app with the spinner stuck on.

The audit that drove the eight fix/audit-* PRs was good work. It found real bugs, and the P1 fixes (popup XSS, availability failures reported as 0%, the UTC and DST timestamp bug) are correct and worth keeping. The problem is what happened in the last mile. The audit said "a sensible file-size limit" and "establish a bounded request contract", and the implementations turned those into hard numbers nobody measured. The audit's own words on the trips chart were "Backend response limits and maximum practical periods were not established by this audit". The implementation shipped 31 days anyway.

1. The spinner can stick on and zones never arrive

High Reproduced src/poll-api/requestScope.js:26

This is the one real bug, as opposed to over-caution. It is an interaction between two changes that were each reviewed on their own and never reviewed together.

PR #15 added scopedMetadataStore, which wraps the Redux store and silently drops any dispatch if the selection changed since the request started. The selection it watches is token, filter.gebied, filter.zones, and layers.displaymode.

The next day, 6d572760 (regional presets) added a multi-municipality branch to updateZones that dispatches SHOW_LOADING: true, awaits a fetch, then clears up in a finally block. Every dispatch in that finally goes through the guard. If you change the data layer while the zones request is in flight, the guard eats all of them.

Here is the dispatch sequence, from a reproduction I ran against the real modules:

healthy:   SET_ZONES(0)  SET_ZONES_LOADED(false)  SHOW_LOADING(true)
           SET_ZONES(1)  SET_ZONES_LOADED(true)   SHOW_LOADING(false)

displaymode changes mid-flight:
           SET_ZONES(0)  SET_ZONES_LOADED(false)  SHOW_LOADING(true)
           ...and nothing else. The last three are dropped.

The end state is zones_loaded: false, an empty zone list, and showloading: true. The global spinner stays on. Because the zone geodata effect in App.tsx is gated on metadata.zones_loaded, zone geometry never loads either.

Nothing recovers it. The updateZones effect depends on [isBeleidszonesPath, isLoggedIn, metadata_loaded, metadata.gebieden, filter.gebied, beleidszonesFilterZones]. It does not depend on displaymode at all, and on any page other than beleidszones it does not depend on filter.zones either. So the guard blocks completions for two keys the effect never re-runs on. You have to change municipality to get out of it.

What I would do. The supersession guard (owners.get(channel) === owner) is the part that earns its keep, and it is correct. The selection() === initial comparison is the part that misfires. Either drop it and rely on supersession, or narrow it to the keys the effect actually re-runs on. Either way, SHOW_LOADING: false should never be droppable. A guard that can strand the UI in a loading state is worse than the stale data it was added to prevent.

2. The trip distance chart refuses most of your date presets

High Reproduced src/api/trips.js:6

This is the CSV problem again, in a different file. PR #20 added MAX_TRIP_DAYS = 31, MAX_TRIP_BYTES = 10 MB, and MAX_TRIPS = 50000. The day cap throws before any request is made.

The date picker offers eight presets. I ran each one through the real getTripsWithDistance:

Vandaag              OK
Laatste 7 dagen      OK
Laatste 30 d         OK
Laatste 90 dagen     BLOCKED  "Kies voor ritafstanden een periode van maximaal 31 dagen."
Laatste 12 maanden   BLOCKED
Dit jaar             BLOCKED
Vorig jaar           BLOCKED

"Laatste 30 d" passes with zero margin. It computes to exactly 31 days, so it sits right on the boundary. Any seasonal comparison is off the table.

The 10 MB streaming guard and the response validation in the same commit are worth keeping. Checking response.ok, rejecting a malformed body, and surfacing a real error with a retry button all fix genuine defects. The day cap is the only part that removes a capability, and it is the part with no evidence behind it.

What I would do. Raise or delete MAX_TRIP_DAYS and let the byte budget do the limiting, since that one is at least tied to something measurable. If the backend does fall over on 90 days, you will find out from the error path that this same PR added, which is the right way to learn it.

3. One malformed vehicle throws away the whole snapshot

High Reproduced scripts/collect_voi_vehicles.py:81

to_geojson raises on the first vehicle with a missing location, an out of range coordinate, or a non-boolean is_non_operational. It raises for the whole payload, not for the record. I fed it a realistic 973 vehicle response with one bad entry at index 500:

healthy snapshot             -> 973 positions
one null is_non_operational  -> ENTIRE SNAPSHOT LOST
one null latitude            -> ENTIRE SNAPSHOT LOST
one missing location         -> ENTIRE SNAPSHOT LOST
one out-of-range longitude   -> ENTIRE SNAPSHOT LOST

What makes this worse than a normal fail-closed choice is that the loss is permanent. The cron runs with restartPolicyType: "NEVER", and voi_database.main() computes floor_to_interval(utc_now()) fresh on every run. A failed 15:00 boundary is never retried, because the 15:10 run asks for 15:10. There is no backfill anywhere in the pipeline.

You already care about this. Your own recovery log from this morning counts the damage: "only 15:00Z and 15:10Z are missing". That was a database outage rather than a bad record, but the failure mode is identical and so is the cost.

What I would do. Skip the bad record, count it, and put the count in the snapshot so a bad day is visible in the data instead of absent from it. Losing 973 good positions to protect yourself from one bad one is the wrong trade for an archive whose entire value is continuity. required_bool is the most brittle of the three, since it turns any upstream change in that one field into a total collection outage.

4. The Voi-only default has stopped re-applying

Medium Reproduced src/AppProvider.js:37

PR #17 made APPLY_PUBLIC_DEFAULT_FILTERS a no-op once public_defaults_applied is set, which is reasonable on its own. Then AppProvider.js added this:

if (persistedState.filter) persistedState.filter.public_defaults_applied = true;

Any visitor with a saved filter now has the flag forced on at boot, so the Voi-only default can never run again. Before PR #17, the old validatePersistedState returned {} for a logged-out visitor, which threw the filter away and re-applied the Voi default on every single public load. That was crude, but it was self-healing.

The consequence is subtle. aanbiedersexclude is a list of operators to hide, so it only ever names the operators that existed when it was written. A new operator appearing in the ACL is not in that list, and the default that would have excluded it is switched off. I simulated a returning public visit with a new operator baqme in the ACL:

persisted aanbiedersexclude : check,donkey
after APPLY_PUBLIC_DEFAULTS : check,donkey        (unchanged, the action is a no-op)
expected for a Voi-only map : check,donkey,baqme
new operator visible on the Voi map: yes

What I would do. This one is genuinely a judgement call and it depends on what you want the public view to be. If it is "my Voi monitor", the default should re-assert itself and the fix is to express it as "keep only Voi" rather than "exclude this frozen list". If it is "a starting point I then adjust", the current behaviour is correct and you can leave it. I lean toward the first, because the fork's entire purpose is Voi and a silently appearing competitor on the map is a confusing way to find out that a new operator launched.

Worth noting that the rest of PR #17 improved things. Keeping the filter for logged-out visitors is better than discarding it, and dropping the random-municipality-on-login is better for you specifically, since you always want the same region.

5. Playback prefetch is aborted at the moment it becomes useful

Medium src/pages/VoiVehicleHistory.tsx:379

PR #19 is mostly a real improvement. Separating displayedSnapshot from selectedSnapshot fixes the genuine bug where the timestamp label disagreed with the map, and gating playback on frame readiness is the right call. The prefetch, though, cancels itself.

The prefetch effect depends on selectedIndex and its cleanup calls controller.abort(). So when the 900 ms timer advances the index from N to N+1, the cleanup fires and aborts the in-flight download of frame N+1. The effect then re-runs, sees displayedSnapshot !== selectedSnapshot, and returns early. The foreground loader starts the same download again from scratch.

The prefetch only helps when the download finishes inside 900 ms, which is exactly the case where you did not need a prefetch. When a frame is slow, which is the case the prefetch exists for, it is cancelled and restarted. You pay for a wasted connection on every frame and get no speedup.

Separately, maxFrames = 4 is tight for a scrubbing viewer. Step back five frames and everything re-downloads. The audit asked for a bounded cache, not a small one, and at roughly 973 points per frame the 20 MB budget will not be the binding constraint anyway.

6. Nine months of data behind a 31 day window

Medium scripts/voi_availability.py:15

Three caps line up at the same number. MAX_WINDOW_DAYS = 31 rejects a wider /availability request with a 400. /index.json has LIMIT 4501 and returns 413 above it, which is the same 31 days at ten minute intervals. The chart UI only offers 24 hours, 7 days, and 31 days.

Both server caps came from PR #21, the audit's proposal 10, on the same day you shipped the area chart whose longest preset is 31 days. So this is another audit-added ceiling rather than something the feature needed. They are at least consistent with each other, which is more than the other limits in this report can claim. But AGENTS.md says the 5 GB volume holds about nine months and retention is indefinite. So the system is designed to accumulate data that nothing can read. Seasonal questions are the obvious ones to ask of a year of bike positions, and right now you cannot ask them without going to the database directly.

The 31 day cap also does real work, since 4464 points is already more than a line chart can usefully draw. The answer is probably not a bigger cap but a coarser bucket. If the endpoint could aggregate to hourly or daily for long windows, a year would be 365 points and cheaper to compute than a day is now.

7. A CSV import hides half the filter bar

Medium src/components/Filterbar/FilterbarRentals.jsx:61

This is from PR #18, the same commit whose size limits you already reverted. While a CSV import is active it hides the Plaats fieldset, the Zones fieldset, the date filter, the duration filter, the distance filter, and the origin/destination toggle, forces direction to herkomst, and removes the HB layer option.

The reasoning is sound. Imported rows are park events and the map selections do not constrain them, so leaving the controls live would imply a filter that is not being applied. But hiding six controls is the heaviest available response, and you reverted the other half of this commit specifically because it decided things on your behalf. The Plaats filter in particular is something you were working on as recently as today's commit.

Disabling them with a one line explanation would carry the same information without making the UI shift under you. The state handling underneath is careful, for what it is worth. csv_previous_direction is saved and restored correctly, it is stripped before the state is persisted, and it does not leak into API parameters because pollTools reads from a fixed field list.

8. One request per day, and failures only reach the console

Medium src/api/operationalVehicleStats.ts:63

This is your own feature from 51c49558, not an audit PR, and it landed after the audit baseline so nobody looked at it.

getOperationalVehicleCountsByDay makes one park_events request per day in the selected period, four at a time, and downloads the full vehicle payload for each day to count non-defect vehicles. The ontwikkelingaggregatie === 'day' gate saves you on the long presets, since "Laatste 12 maanden" and "Dit jaar" switch to week and month aggregation. But "Laatste 90 dagen" stays on day aggregation, so that is 90 requests in 23 sequential rounds. A hand-picked range with day aggregation has no ceiling at all.

The error handling is the part I would fix first:

catch (error: any) {
  if (error?.name !== 'AbortError') {
    console.error('Unable to load available vehicle chart data', error);
  }
}

A failure leaves the chart rendering without its non-defect series and says nothing. That is the same defect class as F01 in the audit, where a failed availability request became a confident 0%. The audit caught it in the KPI and fixed it there. This chart has it too and was never examined.

The contrast with finding 2 is the thing worth sitting with. One chart refuses 90 days outright on a guess about backend load. Its neighbour quietly fires 90 authenticated requests and hides the failures. Both shipped within 24 hours of each other.

What holds up well

Solid

It would be a bad audit that only listed problems, so here is the other side. Most of this fortnight is good work.

  • The P1 popup fix is complete and correctly scoped. Every popup path carrying external data now uses setDOMContent. The only remaining setHTML calls are in src/components/Features/demo/, which the audit explicitly said to skip because they have no external input. Someone read the instruction and followed it rather than converting everything for tidiness.
  • F01 and F02 were real bugs and are properly fixed. A failed availability request used to become a confident 0% KPI, and request timestamps were being shifted by the browser offset and then stamped Z. Both would have quietly produced wrong numbers for as long as you used the app.
  • The region zone filter fails closed correctly. getRegionZoneIds returns [] when boundaries are missing, and the caller turns that into zone_ids=0, a deliberately non-existent ID. The obvious mistake here would be sending no zone filter and getting national data back. Whoever wrote it saw that and handled it.
  • PR #14 is the best of the eight. Dropping gh-pages, the npm CLI as a runtime dependency, and the unpinned npx npm-force-resolutions preinstall step all removed real fragility. Deleting the CRA "learn react" test was right, since it asserted a link that no longer exists. Shimming configureStore out of plain redux instead of adding @reduxjs/toolkit for one test is exactly the proportionate call for a fork with one user.
  • The PostGIS schema is well built. GIST index on geometry, btree on captured_at, a foreign key from positions to snapshots, and captured_at as the primary key so a re-run at the same boundary is idempotent. The column comments say what NULL means, which is the thing people always leave out.
  • The CROW merges were handled carefully. f75928ae kept the region-aware ACL check alongside the upstream admin exemption and added regression tests for all three regions plus partial access. That is the situation where fork work usually disappears, and it did not.
  • Renaming "Beschikbaar" to "Operationeel" in 9181f356 was a good catch. Non-defect does not mean available, and the schema comment already said so. Fixing the label rather than the data was the right direction.

How I would sequence this

Fix first. Finding 1, because a stuck spinner with no recovery is the only thing here that can make the app unusable in a session. Then finding 3, because every day it stays gives you more chances to lose a snapshot you cannot get back.

Then revert. Findings 2 and 7 are the rest of the same commit family you already started unwinding. Finding 2 is a single constant.

Then decide. Finding 4 is a real product question about what the public view is for, and I do not think there is a correct answer without your input. Finding 6 is worth doing properly as aggregation rather than as a bigger number.
